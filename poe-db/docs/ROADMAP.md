# Дорожная карта до цели мастер-промпта (обновлено 24.11.2026, после сессий 7–11)

Цель: локальная лаборатория PoE 1 3.30, которая по запросу проектирует сильные и удобные билды, сама исследует механики, находит нетривиальные синергии и проверяет их воспроизводимыми экспериментами. Работает без LLM API, короткими сессиями Desktop-агента. Успех измеряется точностью прогнозов, долей корректных билдов и подтверждёнными находками, а не объёмом кода.

## 1. Где проект сейчас

| Слой мастер-промпта | Есть | Чего нет |
|---|---|---|
| A. Основа | PoB 2.68.1 headless, правки `--changes`, пакетный режим `variants`, снимки данных, `doctor`, 240 тестов, `build` с ревизиями, компактный `bootstrap`, `--help` групп, коды ошибок | Скорость команд (отдельная сессия, 24.11.2026) |

| F. Зрелость | `eval` (17 кейсов), `observe`, `lab bench` (3 задачи; `empirical` 61% против агента 39%) | ≥ 20 held-out задач; регулярные deep-research сессии; игровые проверки |

Три главных ограничения сейчас:
1. Прототипы генератора — эскизы: дерево жадное, предметы типовые, атаки занижены (локальные моды оружия не экспортируются). Нужен WP6.
2. Новизна и принципы пока не замкнуты в цикл: метрика есть, но не управляет поиском (WP8); принципы из корпуса извлечены, но на held-out проверены только 3 (WP7).
3. Качество измерено слабо: 3 задачи бенчмарка, нет игровых проверок; улучшение системы пока нельзя доказать (WP4, `observe`).

### WP1. BuildCard — структурированный снимок билда — 2 сессии — ГОТОВО (часть 1: `build card`; часть 2: `buttons`, `damage.conversion`, `build card diff`, schema 2)
- `build card <xml> [--out]` (новый модуль `build-card.mjs`, только локальный код). Поля:
  - класс, восхождение, основной скилл, типы урона и цепочка конверсии (по breakdown PoB);
  - оси масштабирования (по `analyze stats` и абляции);
  - слои защиты: max res, armour, evasion, block, suppress, MoM, EHP и max hit по типам;
  - восстановление (regen, leech, recoup), ресурсы и reservation;
  - ключевые уники и keystones, включённые условия конфигурации, уровень и бюджет;
  - `signature` для дедупликации, `pob_sha256`, версии, источник.
- Опция `--ablate` подмешивает классы core/replaceable из `analyze ablate` (разделение Core / Implementation / Replaceable из 3A.3).
- Хранение: JSON-файлы `research/lab/cards/<pob_sha256[0:16]>.json` (локально); SQLite — когда карточек станет сотни. Часть 2 (24.11.2026): `buttons` — оценка нажимаемых клавиш по флагам активных скиллов PoB (`active_skills` из pob-worker: triggered/aura/herald/reservation/minion/totem/trap/mine/brand/movement/guard/...) и флаконам ("Used when", Mageblood, life/mana — только в верхней границе), `estimate`/`minimum`/`maximum` + `uncertainty`; `damage.conversion` — ссылки convert/gain_as и цепочки из `conversionTable` основного скилла PoB (по рукам для атак, миньон для minion-билдов), без пересчёта, иначе `null` + `conversion_reason`; `build card diff <a> <b>` — структурная разница; `schema_version: 2`, карточки v1 читаются (`not_in_card`), сигнатура не изменилась. Существующие карточки корпуса не пересчитаны: v2-поля появятся при следующем `build card --save`/`corpus add`.
- Готово: карточки для 3 reference-примеров и основного билда, детерминированность (повтор → тот же hash), тесты на фикстурах.

### WP3. Контрфакты: условия, uptime, взаимодействия — 1 сессия, параллельно с WP1 — ГОТОВО (`--kinds config`, `analyze interactions`, `lab import interactions`)

- `analyze interactions <xml> --top N`: для core-компонентов пары (и тройки для top-3) — `loss(AB) − loss(A) − loss(B)`. Неаддитивность становится измеримой; это синергии из разделов 3 и 8.
- Авто-запись в `lab` (`lab import ablation|interactions`).
- Готово: на основном билде список условий с потерей DPS и ≥ 3 измеренных пар с ненулевым взаимодействием; тесты чистой логики.

### WP5. Architecture Blueprint и генератор (Build Request Mode) — ГОТОВО по критерию (итерация 2, 24.11.2026); доработки — в WP6/WP8
1. Схема `Blueprint` (в `build.json` design или запись `lab`): цепочка урона, оси масштабирования, слои защиты, ресурсы, требования к uptime и кнопкам, критерии успеха из профиля пользователя.
2. Генерация: active gems из knowledge DB по тегам и ограничениям профиля (например, темы, ограничения на кнопки, выбранные восхождения) → совместимые supports (существующий фильтр типов) → узлы под оси через `tree search`/`tree path` → шаблоны защиты.
3. Жёсткие фильтры: требования, reservation, mana sustain, доступность уников, бюджет по ценам (без смешения валют).
4. Прототип: `pob new` + `--changes` (уже есть) с типовыми редкими предметами из `item build` (легальный пул) → `pob run`.
5. Оценка по осям: sustained DPS, max hit по типам, EHP, sustain, кнопки, бюджет, `analyze report` T17. Pareto-фронт, причины отсева — в `lab` (`failure`).
- Готово: по профилю пользователя ≥ 5 разных архитектур-прототипов с PoB-числами, фронт и отказы сохранены; на синтетическом запросе воспроизводится известный reference-архетип (проверка генератора).
- Статус (24.11.2026, итерация 2): ГОТОВО по критерию — `design request|candidates|generate|verify|show` (`scripts/design-blueprint.mjs`, `design-kit.mjs`, `design-generate.mjs`, тест `test/design.test.mjs`; описание в ENVIRONMENT.md). Пробный прогон по профилю: 748 кандидатов -> 24 скрининг -> 10 прототипов с PoB -> 10 прошли фильтры и валидатор WP9, фронт из 7. Помогли ремонты: броня даёт недостающий атрибут, реген маны в комплекте при «без флаконов», цикл «аура для маны в любом слоте / снять поддержку». Проверка генератора: `design verify --example poison-srs-balormage-330-5744fd01 --prototype` — SRS Necromancer доходит до прототипа и во фронт (без имени скилла; run `2026-11-24T08-47-05-necromancer`); Toxic Rain Pathfinder — ранг 3 среди кандидатов; Tornado Inquisitor — нет (ранг 51/82). Записи `lab` F-001…F-021 — отказы ранних прогонов этой сессии, устарели (в итоговом прогоне отказов нет).

### WP5b. Основы билдостроения из корпуса — ПУНКТЫ 1–6 СДЕЛАНЫ (eldritch implicits в комплекте — нет; прогон после п. 5 — 24.11.2026: кластер и автофлаконы в прототипах, но фильтр `unparsed_item_mods` ловит строку Instilling)
Проблема (проверено подсчётом в `design-*.mjs`: атрибуты 25, regen 13, mastery 2, leech 0, eldritch 0, cluster 0, автофлаконы 0): генератор чинит ману и атрибуты ручными правилами и строит дерево с нуля по кратчайшим путям. Отсюда реген маны вместо leech, переизбыток атрибутов, нет eldritch implicits, masteries, cluster jewels, автоиспользования флаконов (Wickerman, Enkindling/Instilling и т.п.), keystones без архетипа, странные деревья. Принцип: решения брать из норм реальных билдов корпуса, а не из правил, написанных вручную.
1. `corpus norms [--ascendancy X] [--skill-tag T] [--form hit|dot]`: по корпусу с фильтром качества — источники sustain маны/жизни (leech, regen, masteries, Eldritch Battery, flasks), запас атрибутов над требованием, доля eldritch implicits, cluster jewels, число masteries, автофлаконы, типичные keystones по архетипу; недостающие поля — из XML PoB, при необходимости обратно совместимое расширение BuildCard.
2. Проверка основ для прототипа: отклонения от норм как предупреждения в `design verify` и `analyze report` (например «реген маны при отсутствии leech», «+150 лишних атрибутов», 0 masteries, нет автофлаконов при норме и т.д.).
3. Посев: прототип стартует с дерева и экипировки ближайших билдов корпуса (`novelty.mjs`, соседи) вместо построения с нуля; дерево — правка готового через PoB (`removeNodes/addNodes`, Node Power), а не BFS от старта.
4. Ремонты маны/атрибутов — кандидаты из норм (leech-узлы/mastery, eldritch implicit, cluster, суффикс на редком предмете), старые правила только как запасной вариант.
5. Сборщик предметов: поддержка eldritch implicits (Searing Exarch / Eater of Worlds) и cluster jewels (малый/средний/большой, notables) в легальном пуле `item build|pool`; автофлаконы (Wickerman, Mageblood-подобные, enchant «used when…»).
6. Сравнение прототипов до и после WP5b по PoB-числам и числу предупреждений; результаты и отказы — в `lab`.
- Готово: `corpus norms` работает; прототипы профиля проходят проверку основ без грубых отклонений (или с объяснением); хотя бы один прототип использует leech/mastery, eldritch implicits и cluster jewel там, где этого требует норма корпуса.
- Сделано (24.11.2026): BuildCard.foundation (`scripts/build-foundation.mjs`) и дозаполнение 151 карточки корпуса; `corpus norms` по группам и `corpus norms --check <xml>` (группа норм: восхождение+тип скилла → тип → восхождение → корпус); проверка основ в каждом прототипе `design generate` и в `analyze report`; посев от ближайшего билда корпуса (`scripts/design-seed.mjs`, `design generate --seed both|only|none`, в `design verify` выключен); masteries в прототипах с нуля (резерв очков = медиана нормы, эффекты пробует PoB). Находки корпуса: атаки держат ману leech (81%), заклинания — регеном (100%); eldritch implicits в PoB гайдов редки (15%), cluster jewels 72%, автофлаконы 69%, медиана 8 masteries. П. 5 (24.11.2026): автофлаконы — 5 флаконов комплекта (`flaskPlan` в `design-kit.mjs`: life реактивный, 4 utility с Instilling "Used when Charges reach full" и `replace_items[].active`; основы по частоте в корпусе); cluster jewels — `scripts/design-cluster.mjs`: всё пространство из данных PoB (`ClusterJewels.lua`: 55 зачарований Large/Medium/Small; `ModJewelCluster.lua`: 301 notable, легальность по весу тега зачарования, prefix/suffix), формы по норме корпуса (Large 8/2 гнезда/2 префикса + 1 суффикс, Medium 5/1/2, Small 3/0/1), ранжирование осями генератора, PoB-проба лучших кандидатов в двух ближайших внешних гнёздах на резерве 12 очков, если норма группы ≥ 50%; `pob-edit.lua` ищет notables по имени внутри подграфа гнезда. Нет: средние/малые кластеры во вложенных гнёздах большого, аффиксы «also grant», eldritch implicits. П. 6 сделан (E-006: посевные прототипы — 0–1 предупреждение об основах против 4–5, выше EHP и max hit).

### WP6. Совместная оптимизация — ПЕРВЫЙ ШАГ ГОТОВ (24.11.2026: `design optimize`, обмены узлов дерева)
- Дерево: beam/greedy по Node Power на очко с учётом стоимости пути и бюджета; возврат при ухудшении.
- Чередование: дерево ↔ supports ↔ слоты (coordinate ascent поверх `analyze nodes/upgrades`), многоцелевой отбор с ограничениями защиты.
- Готово: на прототипе из WP5 улучшение по фронту без нарушения жёстких ограничений; все шаги воспроизводимы из `lab`.
- Сделано (24.11.2026): `design optimize <xml>` (`scripts/design-optimize.mjs`) — в каждом раунде PoB считает ценность снятия каждого выделенного узла (removeNodes, с зависимыми; листья отдельно) и Node Power достижимых notables/keystones, обмены проверяются комбинированными вариантами PoB, лучший допустимый (EHP и max hit не ниже 0.97 старта, мана не уходит в минус, без новых невыполненных требований, в бюджете очков) применяется настоящей правкой дерева. H-003: на прототипе с нуля за 3 раунда DPS +14.6%, EHP +25.5%, max hit +55.7%; оптимизатор убрал узлы миньонов, взятые жадным деревом для заклинания (ошибка `nodeValue` исправлена: строки миньонов и оружейные условия считаются построчно). Узлы с условиями (EO: «crit in the past 8 s») помечаются `check_conditions`. Дальше: чередование дерево ↔ supports ↔ слоты, несколько обменов за раунд.

### WP7. Принципы из корпуса — КАНДИДАТЫ ГОТОВЫ, ПЕРВАЯ ПРОВЕРКА НА HELD-OUT СДЕЛАНА (24.11.2026)
- Локальная статистика: признаки BuildCard × классы абляции по корпусу → кандидаты (association rules, частоты с контрпримерами).
- LLM только формулирует и проверяет кандидатов; проверка — абляцией или переносом на held-out билд. Статусы — только через гейты `lab`.
- Готово: ≥ 5 принципов `experimentally-validated`, ≥ 1 `generalized` (2 билда + условия), отрицательные результаты сохранены.
- Сделано (24.11.2026): `corpus principles` (`scripts/corpus-principles.mjs`) — условные кандидаты «компонент × контекст» (тип скилла, hit/DoT, тип урона, пул защиты, источник маны, восхождение) по абляциям корпуса: доля core/major в контексте против вне его (≥ 3 билдов с каждой стороны), опоры и контрпримеры; `--record N` пишет в `lab` гипотезы. Примеры: Withered несёт chaos-билды (100% против 33%), Shocked — lightning (96% против 46%), Iron Will не несёт заклинания. Дальше: проверка лучших кандидатов абляцией held-out билдов через гейты `lab`.
- Проверка (24.11.2026, модель на 135 билдах, 239 кандидатов, топ-10 записаны в `lab` гипотезами). Held-out — билды корпуса, исключённые фильтром качества (их нет в модели), и билд вне корпуса; прогноз записан до расчёта. MoM × hit — `supported`: core внутри контекста (защита −30.5%), minor вне его (DoT, −4.7%). Shocked × Lightning — `supported` на одном билде внутри контекста (major, DPS −13%), сторона вне контекста не проверена; принцип близок к тавтологии конфигурации. Inveterate × mana leech — `refuted`: minor (DPS −0.6%) на held-out билде с leech. Ограничения: held-out билдов мало (15, в основном низкого уровня), для части кандидатов (Lightning Golem × Elementalist) подходящих нет; верхние места топа заняты тавтологиями конфигурации — нужен фильтр «условие конфигурации ≈ тип урона».

### WP8. Новизна и reverse theorycrafting — ЧАСТИ 1–2 ГОТОВЫ (метрика, ось генератора, `design reverse`)
- Структурная сигнатура (источник урона, оси, модель защиты, sustain, ключевые цепочки) → расстояние до корпуса и `meta` → `novelty`, отдельно от performance; Pareto по двум осям.
- Reverse: цель («−X% res противника», «иммунитет к freeze без флакона», «свободный слот») → несколько независимых путей из stat search по дереву, уникам, модам и камням с ценой каждого пути.
- Сделано (часть 1, 24.11.2026): метрика структурной новизны `scripts/novelty.mjs`, `corpus novelty <xml|card.json>` (вектор из BuildCard → взвешенное расстояние до корпуса с фильтром качества → `novelty` 0..1, полоса, соседи и отличия), `noveltyScore(card, corpus)` для генератора; тесты `test/novelty.test.mjs`. Дальше: подключить `noveltyScore` в `design generate` (флаг `--novelty`, вторая ось Pareto), сравнение с `meta` (частота архетипа в корпусе), калибровка весов на парах «вариант/другой архетип», reverse theorycrafting.
- Сделано (24.11.2026): новизна каждого прототипа (`noveltyScore` по BuildCard прототипа) — ось Pareto в `design generate` (по умолчанию, `--no-novelty` выключает); `design reverse "<цель>" [--xml]` — обратный теорикрафт: все источники цели (дерево и masteries с ценой в очках от текущего дерева, анойнты, уники с нижней границей цены, моды предметов и флаконов, крафт, тату, viscera, Pantheon, Foulborn, supports). Дальше: калибровка весов новизны, автоматическая оценка путей reverse через PoB.
- Готово: генератор с режимом `--novelty` выдаёт кандидатов, отличающихся от корпуса структурно (а не заменой предметов), с performance-профилем и пометками неподдержанных механик.

## 3a. Правило разделения труда и аудит дублирования (24.11.2026)

Правило: перебор, расчёты, сравнение и хранение — код, базы и PoB; модель выбирает вопрос, формулирует гипотезы и прогнозы, интерпретирует то, что инструменты не классифицируют. Перед новой функцией искать штатную функцию PoB (калькулятор с override, вкладки предметов/камней/дерева) и существующий модуль.

Найдено и исправлено:
- Изоляция узлов отрицанием статов (`custom_mods`) дублировала штатное сравнение узлов PoB → заменена на `remove_nodes` (`GetMiscCalculator` + `override.removeNodes`, как подсказка дерева), код отрицания удалён; числа совпали, теперь точно и для keystones/masteries.
- Снятие узлов через `deallocate` для абляции заменено тем же механизмом (дерево не правится, ветка — через `node.depends`).
- Пробы «снять support» в `analysis-candidates.weakestSupport` и в абляции — теперь один план (`planAblation`) и одно определение support (данные PoB, `isSupportGem`).
- Граница журнала `lab` с `build.json`/`observe`/`mechanics` описана в ENVIRONMENT.md.

Оставлено осознанно: `tree path|cost` (собственный BFS по правилам PoB) нужен для офлайн-планирования без движка и проверен независимо; классификация в `build card` — правила поверх чисел PoB, а не пересчёт.

WP0b — ГОТОВО (24.11.2026): `variants`/`node_power` в воркере, `runVariants`; абляция дерева и `analyze nodes` переведены, собственный BFS кандидатов удалён. ## 5. Риски
- PoB не моделирует часть механик (взрывы, recoup, reflect): находки на них остаются `mechanically_valid`, не `simulator_verified`, и требуют игрового теста через `observe`.
- Пространство поиска огромно: генератор ограничивается шаблонами Blueprint и жёсткими фильтрами до PoB-расчётов; бюджет расчётов задаётся явно.
- Маленький корпус даёт ложные принципы: повторяемость считается гипотезой, а статус поднимается только абляцией или переносом.
- Цены устаревают, курсы Chaos/Divine конфликтуют: бюджет без смешения снимков.
